## Part 1 — `Tools/alfa-install.sh` @ `496f0eb`

### Bugs

**1. `device_udids` silently reuses the previous run's device list — line 49**

`xcrun devicectl … --json-output "$DEVICE_JSON"` ends in `|| true`, and line 50 greps
that fixed path unconditionally. Verified: on an unparseable predicate devicectl exits
**64 and leaves the file untouched**. Any devicectl failure — daemon hiccup, a name with
a trailing backslash breaking the predicate, `xcrun` not finding the utility — therefore
resolves to whatever the *last* run cached, and the build installs to the wrong device.

Fix: `mktemp` + trap, and fail on a non-zero exit instead of `|| true`.

**2. `Tools/alfa-install.sh -- -quiet` is broken — line 60**

Verified: `${1:-…}` sees a non-empty `$1`, so `SELECTOR="--"`. Line 61 shifts it off,
line 62 then sees `-quiet` and does not shift again, so control reaches the name branch
and dies with `Expected one paired iOS device named "--", found 0` — while `$ALFA_DEVICE`,
the fallback it was supposed to use, is ignored. That is the exact form the header
documents.

Fix: consume `--` before computing `SELECTOR`.

**3. The 2FA hint never fires for the 2FA case — line 149**

Header lines 22-23 and the comment at 147-148 both describe an *expired session*, but the
grep matches `error: No Accounts`, which is the distinct *never-signed-in* case. An expired
session emits `Communication with Apple failed. Your session has expired.` and falls
through to the generic `tail -40`. The one message written to save a log dive is the one
that does not print.

Fix: match on `Communication with Apple failed|session has expired|No Accounts`.

**4. `REACHABLE` cannot break the tie it was added for — line 44**

Verified on this machine: **both paired devices report `transportType: localNetwork` with
nothing plugged in**. The predicate matches every remembered device, so two-device
ambiguity still lands in the error branch. The predicate, its five-line comment, the second
query, and the `(( ${#matches} )) ||` fallback all buy nothing over a single `$PAIRED_IOS`
query.

### Smaller

- **line 153** — "paired but not reachable" is asserted for a UDID passed as an argument,
  which the script never pairing-checked. A typo'd UDID sends the user hunting for a cable.
- **line 71** — NSPredicate `==` is case- and whitespace-exact. `ALFA_DEVICE=monad` prints
  "found 0" above a listing that visibly contains `Monad`. `==[c]` fixes it.
- **line 91** — the count comes from the reachable-filtered query but the listing prints all
  paired devices; 3 paired / 2 reachable prints "found 2" above 3 rows.
- **line 91** — with zero paired devices it says "name the one you want" and prints an empty
  list. Naming cannot help; the useful advice (pair, trust, enable Developer Mode) never
  appears.
- **line 85** — up to three `devicectl` round-trips on the success path, the third purely to
  print the `Device:` line. The line-49 JSON already carries `deviceProperties.name` next to
  the udid.
- **lines 72, 85, 86** — `matches=(${matches:#})` is dead code, three times. Verified: zsh
  already drops empty fields from an unquoted `${(f)…}` array assignment.
- **lines 36, 50, 51** — the UDID hex pattern written out three times, and inconsistently
  anchored (36 is anchored, 50 and 51 are not).

### Cross-file

**Device selection has diverged three ways.** `alfa-install.sh` now takes `ALFA_DEVICE` by
name; `Tools/alfa-logs.sh:15` still honours only `ALFA_DEVICE_UDID` and still auto-detects
through `xcrun xctrace list devices` — the DVT listing that `6b8789e` abandoned precisely
because it files reachable devices under `== Devices Offline ==`; `Tools/ble-integration/on-device-it.sh:19`
hardcodes a UDID. Follow the new docs and install works while logs still fails. A shared
`Tools/lib/device.zsh` sourced by all three is the right depth.

### Note on the out-of-tree refresh agent

`~/.nix/scripts/ios-sideload-refresh.sh` has the same `|| true` shape in its `device_udids`,
but it writes to a `$$`-suffixed path and `rm -f`s it, so a devicectl failure yields empty
and the agent skips rather than targeting a stale device. Safe today; a reused PID after a
`kill -9` is the only hole.

## Part 2 — whole repository

Scope: all 30 Swift sources (~6k lines), `project.yml`, `Tools/`, and the docs' load-bearing
claims. `swift test` in `AlfaKit` is green — **97 tests, 10 suites**. Findings 1, 2 and 9 were
confirmed by running throwaway reducer tests against the real engines, not by reading alone.
`AlfaCameraSim` was reviewed at lower depth (dev-only tool).

**Status (2026-08-16).** 1, 2 and 5 are **fixed**; 1 and 2 carry regression tests confirmed to fail
against the pre-fix source, and 5's cadence was verified on device against a live A7R V. **3 was
refuted** by the device trial and no fix shipped. Finding 13 is new — it came out of that trial; its
diagnosis was **confirmed on device** and it is now fixed by rebuilding a stale link, which no host
test can cover.

### Bugs

**1. FIXED — One `02 C3 00` disables the whole Remote tab until the app is relaunched**
`AlfaKit/Sources/SonyBLE/RemoteControlPolicy.swift:281`

`remoteFeatureInactive` sets `remoteFeatureActive = false`, and the only thing that clears it is
"any other FF02 traffic" (line 307). `.connectionChanged` resets `focus`, `isRecording`,
`recordingStartedAt` and `exposureStartedAt` — but **not** `remoteFeatureActive`. Confirmed by
test: after `connected → 02 C3 00 → backedOff → connected`, the flag is still `false` and
`shutterAutoSequenceRequested` returns **0 actions**. The user turns the camera's Bluetooth
remote setting on, reconnects, and every control stays inert — and because Alfa now sends
nothing, the camera has no reason to emit the FF02 traffic that would unstick it. Only a physical
press on the body, or an app relaunch, recovers.

Fix: reset `remoteFeatureActive = true` when `.connectionChanged` enters `.connected`.

**2. FIXED — A locked AF-ON is abandoned without a release, and the retry sends a second press**
`AlfaKit/Sources/SonyBLE/RemoteControlPolicy.swift:275` and `:383`

`abandonTransientState` drops `afOn`/`c1` to `.idle` and emits no release. That is right for
`remoteFeatureInactive` and for a disconnect; it is wrong for `.commandWriteFailed`, which fires
on *any* rejected FF01 write — including a transient one on a live link. Confirmed by test: lock
AF-ON → `[1, 21]` (`01 15`, press) goes out → an unrelated write fails → `afOn` becomes `.idle`
with no release → the user taps the lock again and gets **`[1, 21]` again**, never `01 14`. The
camera is left with AF-ON physically held and the UI offers no way to lift it.

The comment ("more writes are pointless or harmful") is true of the other two callers and
over-generalised to this one.

**3. NOT A BUG — A Bluetooth off→on cycle permanently blocks reconnection**
`AlfaKit/Sources/SonyBLE/CameraLink.swift:613`

`centralManagerDidUpdateState` only forwards availability. `clearPeripheralState()` is called
from the restore paths, `teardown()`, `didFailToConnect` and `didDisconnectPeripheral` — never
from a state change. CoreBluetooth invalidates peripherals on `.poweredOff` and does not
guarantee a `didDisconnectPeripheral` for it, so `self.peripheral` survives as a stale handle,
and:

- `didDiscover:` line 703 (`if self.peripheral == nil`) never adopts anything again;
- `scheduleScanTimeout`'s `guard peripheral == nil` returns early, so the direct-connect
  fallback never runs either;
- `writeLocation`'s guard still passes (`peripheral != nil`, `writeChar != nil`,
  `handshakeComplete == true`), so pushes are written into a dead handle while the UI reads
  **GEOTAGGING**.

Nothing recovers this short of an app relaunch.

**REFUTED on device (iPad mini 6, 2026-08-16 13:40) — no fix shipped; the speculative change was
reverted.** The premise was that CoreBluetooth may skip `didDisconnectPeripheral` on a `.poweredOff`
transition. It does not, on either path that can hold a peripheral here:

```
13:40:05.715  disconnected: clean                            ← didDisconnectPeripheral DID fire
13:40:05.718  background auto-resume — standing connect to known camera
13:40:05.719  connect failed: Local device is powered off.   ← didFailToConnect on the new intent
13:40:13.586  background auto-resume — standing connect to known camera
13:40:14.327  connected — discovering services               ← recovered, unaided
```

Both delegates already call `clearPeripheralState()`, so `peripheral` is nil long before
`centralManagerDidUpdateState(.poweredOff)` arrives — a guard added there never fires (the trial
fix's log line never appeared). An established link and a pending connect are the only two states
in which `peripheral` is non-nil, because `adoptAndConnect` calls `connect()` immediately, so there
is no third path. Recovery then runs through `begin()`'s existing `.unavailable → .scanning`
branch, which treats `.unavailable` like `.idle` and needs no manual trigger.

Untested corner: `.resetting` (a `bluetoothd` crash), where the delegate story is genuinely
different. Not reproducible on demand, and shipping unverified defensive code is the habit the
"Dead or misleading" section below complains about — so it stays unwritten until something is
actually seen in the field.

**4. Any unrecognised CC05 frame reads as power-off and tears the link down**
`AlfaKit/Sources/SonyProtocol/CameraPowerState.swift:24`

The type's own doc comment says parsing "reports a definitive `.off` … only for a well-formed
frame, and returns `.unknown` for anything it does not recognise so malformed data can never
trigger a spurious disconnect." The implementation returns `.off` for *every* `0x04`-tagged,
≥5-byte frame with a non-zero payload; `.unknown` is reachable only for a wrong tag or a short
frame. `CameraCentral.swift:343` turns `.off` into `.cameraPoweredOff`, which disconnects **and**
backs off — geotagging then stops silently until the user foregrounds the app or taps Sync now.

This matters because `SonyGATT` itself calls CC05 `// power/Wi-Fi state`: a Wi-Fi-state frame on
a powered-**on** camera is exactly the shape that decodes as `.off`. The behaviour is pinned by
`CameraPowerStateTests.nonZeroPayloadIsOff`, so this is a decision to revisit, not an accident —
but the sibling test is literally named "Unrecognised frames are unknown, never a false
power-off", and the doc comment promises what the code doesn't do.

**5. FIXED — One failed write kills the keep-alive for good while stationary**
`AlfaKit/Sources/AlfaGeotag/GeotagCoordinator.swift:485` and `:499`

`armHeartbeat()` is called from exactly one place: the `.locationPushed` case, i.e. a write
**ack**. A write that fails emits `.failure` instead (`CameraLink.swift:904`), so the heartbeat is
never re-armed. Stationary, the distance filter means no new location samples arrive either — so
nothing re-arms it at all. The camera expires its fix ~60 s later ("Location information cannot be
obtained") on a link Alfa still reports as connected. That is precisely the failure the heartbeat
exists to prevent, and finding 3 gets there too (all writes fail silently after a BT bounce).

Fixed by making the chain self-sustaining rather than ack-driven: the heartbeat is armed on
arrival at `.connected` (so a *first* push that fails is covered too) and re-armed by its own tick
after calling `central.heartbeat()`, not only by the resulting `.locationPushed`. A successful
write still re-arms through `.locationPushed`, which cancels and replaces the tick's arm, so the
cadence is unchanged: one fire per `heartbeatInterval` of write silence.

**Verification:** not host-testable — `GeotagCoordinator` is `@MainActor` and constructs a real
`CLLocationManager`, and there is no `AlfaGeotagTests` target. Verified instead on device (iPad
mini 6, live A7R V, app foregrounded and stationary):

```
13:37:19.734  location push → camera (95 B)   → acked
13:38:06.355  location push → camera (95 B)   → acked   (+46.6 s)
13:38:52.860  location push → camera (95 B)   → acked   (+46.5 s)
13:39:38.860  location push → camera (95 B)   → acked   (+46.0 s)
```

Four self-sustaining ticks at the 45 s cadence, no drift and no double-fire — so arming at
`.connected`, re-arming from the tick, and re-arming from the ack compose correctly rather than
stacking timers. **Not** covered: every write in that window succeeded, so the specific regression
(a *failed* write no longer breaking the chain) is still argued from the code, not observed. To
catch it in the wild, look for a `write failed:` line that is not followed by another push ~45 s
later.

**6. `stop()` then `start()` yields a live-looking but dead central**
`AlfaKit/Sources/SonyBLE/CameraCentral.swift:107`

`linkEvents` is one `AsyncStream` created in `init` and never re-made. `stop()` cancels
`consumeTask`, which terminates that stream; a later `start()` builds a new `CameraLink` and a new
consume task over the same, already-finished stream, so no link event is ever handled again.
`start()` is documented "Idempotent", which invites exactly this call pattern. Nothing does it
today — the integration tests build a fresh central per test — so this is latent, but it is public
API.

**7. Remote intents are submitted as unordered `Task`s**
`AlfaKit/Sources/AlfaGeotag/RemoteCoordinator.swift` (every intent method)

Each intent is `Task { await central.… }`. Separately-created unstructured tasks have no ordering
guarantee, and the engine they feed exists specifically to enforce ordering ("the one
protocol-fragile choreography in Phase 2"). The shutter paths happen to be self-healing under
reordering, but the hold buttons are not: `buttonUp` arriving before `buttonDown` leaves the
button `.held` with a press on the wire and the finger already lifted. `RemoteView.swift:352-355`
fires `shutterFullUp()` and `shutterHalfUp()` as two such tasks back to back.

Fix: funnel intents through one serialized channel (an `AsyncStream` into the actor) instead of a
task per call.

**8. `.ready` is emitted before the remote-control service is usable**
`AlfaKit/Sources/SonyBLE/CameraLink.swift:816` vs `:862`

`markReady()` fires off the *location* handshake ack; FF01/FF02 are assigned in a different
`didDiscoverCharacteristicsFor` callback with no ordering between them. A shutter tap in the first
moments after connect therefore hits `remoteCommandChar == nil` and returns
`.remoteCommandWriteFailed("link not ready for remote commands")` — which, per finding 2, also
silently drops any locked button. The integration test already works around this with a literal
`Task.sleep(1s)` and a comment naming the cause
(`Tests/AlfaIntegrationTests/BLEIntegrationTests.swift`). The sleep is the symptom; the fix is
for readiness to account for the services the caller is about to use.

**13. FIXED (device-verifiable only) — after a Bluetooth bounce, a powered-ON camera is parked in standby**
`AlfaKit/Sources/SonyBLE/CameraLink.swift:543` (`handleHandshakeFailure`)

Fell out of the finding-3 trial. The camera was switched **on** throughout, yet:

```
13:40:14.327  connected — discovering services
13:40:15.777  write FAILED on DD30: Unknown ATT error.
13:40:15.777  camera connected but not serving/accepting the Sony GATT (powered off or still
              booting) — holding link in standby (no writes), probing
13:41:18.416  write FAILED on DD30: Unknown ATT error.        ← 60 s standby probe, same failure
13:41:26.105  disconnected: The specified device has disconnected from us.
```

`didBond` is seeded `true` for any remembered camera (`init`, and again in
`clearPeripheralState`), so `handleHandshakeFailure` skips its three spaced retries entirely and
calls `enterStandby()` on the *first* rejected DD30 write. That heuristic assumes a rejected write
on a bonded camera means "powered off" — but a link rebuilt right after the phone's Bluetooth
restarted has not re-encrypted yet, and the ATT error is transient, exactly the case the retries
exist for. The result is a ~60 s dead window (or longer) on a camera that is on and reachable,
under a log line that positively asserts the opposite.

The retries are gated on the wrong question. `didBond` distinguishes *first pairing* from
*re-connection*; what matters here is whether the failure is transient, which the bond state does
not tell you. A bounded retry before concluding "powered off" would cost three seconds and cover
both.

**FIXED — but read the caveat.** `handleHandshakeFailure` now retries up to `maxHandshakeRetries`
regardless of bond state, and `didBond` is deleted (that read was its only one; the field was
otherwise write-only). Against a genuinely off camera the change costs three writes over nine
seconds, well under what the 60 s standby probe already spends on it. The `!inStandby` guard is
unchanged, so a standby probe's own failures still never enter the retry path.

**Diagnosis confirmed, fix insufficient.** A longer collect caught how the incident ended:

```
13:41:18.416  write FAILED on DD30: Unknown ATT error.   ← standby probe, same link
13:41:26.105  disconnected: The specified device has disconnected from us.
13:41:35.242  connected — discovering services
13:41:35.250  services modified (0 invalidated) — re-discovering
13:41:36.691  notify DD01 = 03 01 04 00
13:41:36.826  notify DD01 = 03 01 05 00
13:41:36.893  ready — services + handshake acknowledged
```

That kills the power-save hypothesis: the camera served its full GATT nine seconds after the last
rejected write, with no user action and no power cycle in between. The DD01 bonding traffic on the
fresh link is the re-encryption the stale link never got. The camera was on the whole time — the
*link* was dead.

But the same trace shows the *first* fix does not repair it. Recovery required tearing the link
down; the camera dropped us at 13:41:26 and the reconnect handshook on the first try. The broken
link stayed broken for ~70 s, so three retries over nine seconds would have failed too and entered
standby exactly as before. The retry is harmless and the gate it removed was still asking the wrong
question, but it was never the repair.

**The repair: rebuild the link after three fruitless standby probes.** Standby re-probed the *same*
link forever (`scheduleStandbyProbe`, 60 s), and a link in this state never recovers in place.
`probeStandby` now counts rejected probes and, on the fourth, calls `rebuildStaleLink` — drop the
peripheral and let `didDisconnectPeripheral` → `GeotagPolicy` re-establish, which is precisely the
path that recovered the field case. `clearPeripheralState` zeroes the counter, so the new link
starts fresh.

Two deliberate exemptions keep this from becoming the churn `docs/05` forbids:

- **Reduced GATT is never rebuilt.** No location characteristics at all is the signature of a
  genuinely off "Cnct. while Power OFF" body. That branch holds the link indefinitely and probes as
  before; Service Changed (`didModifyServices`) is still the background power-on detector. Only a
  camera that *is* serving its Sony GATT yet keeps rejecting the handshake is treated as stale.
- **Notification-driven probes don't spend the budget** (`probeStandby(mayRebuild:)`). An incoming
  notification is evidence the link carries traffic, so it must not be the thing that drops it.

Cost against a serving-but-genuinely-unusable camera is one reconnect per ~4 minutes, versus the
indefinite dead window before.

**Not covered by tests.** `CameraLink` is the CoreBluetooth layer and has no host tests — only the
pure reducers do. This is device-verifiable only, and reproducing it needs the original trigger (a
phone Bluetooth bounce against a connected camera).

The sharper discriminator remains the ATT error code, which the write-failure log now carries
(`CameraLink.describe`). `CBATTErrorDomain 5` (insufficient authentication) or `15` (insufficient
encryption) would confirm re-encryption as the cause and could gate the rebuild directly instead of
spending three probes first. That logging was added *after* this incident, so the codes here are
unknown — one more occurrence settles it.

### Smaller

- **Location packets carry a timestamp up to 60 s stale.**
  `GeotagPolicy` restamps to `now` for heartbeat and capture pushes, but `.connected` and
  `.location` push `fix.timestamp` verbatim, and `LocationProvider` admits fixes up to 60 s old.
  Confirmed: a fix ingested 50 s ago produces a push whose packet time is 50 s behind. DD11 always
  carries the clock (`CameraCentral.swift:420`), yet only the CC13 path has a freshness guard
  (10 s). A stationary phone holds one sample indefinitely, so the on-connect push is the worst
  case.
- **Home's footer contradicts the shipped design and the Settings screen.** `App/HomeView.swift`:
  "Alfa never holds the link open in the background, which is what drains the camera battery."
  `backgroundResume` now defaults **on**, holds a standing connect, and holds a dormant link in
  standby — and `UserDefaultsGeotagSettingsStore` migrates old `false` values *to* on, calling the
  old behaviour "a superseded safety model". `SettingsView`'s Background footer says the opposite
  of Home's.
- **"Forget camera" goes dead after "Disable geotagging".** `disable()` nils `cameraName`, which
  is the button's `.disabled` condition, while the camera stays in `UserDefaults`.
  `loadRememberedCameraIfNeeded()` runs once from ContentView's `.task`, so the button stays grey
  until relaunch. `GeotagCoordinator.swift:162`.
- **`gracefulDisconnect` writes DD31/DD30 `0x00` and immediately cancels the connection**
  (`CameraLink.swift:470`), so the `.withResponse` writes rarely land — and if one *does* ack
  while `handshakeComplete == false`, `didWriteValueFor:917` reads it as handshake success and
  calls `markReady()`. The `0x01` handshake writes and the `0x00` teardown writes are
  indistinguishable at the ack.
- **`writeTime` is the only write method without the `handshakeComplete` gate**
  (`CameraLink.swift:327`), and `flushTimeSync()` is invoked from characteristic discovery — a
  path that runs pre-handshake. Safe today only because `.ready` is the sole caller; the
  "never write to a standby camera" invariant is enforced by convention here, not by the code.
- **Every notification while in standby triggers a full `probeStandby()`** (re-discovery or a
  handshake write) with no rate limit — `CameraLink.swift:948`. A chatty standby camera turns the
  deliberately-dormant hold into per-notification churn, which is the thing `docs/05` is about.

### Dead or misleading

- `ConnectionPolicy.stayConnectedWhileCameraOn` and `.backOffInStandby` are **never read** in
  production code — only assigned and asserted in tests. Setting `backOffInStandby = false`
  changes nothing, while reading as the switch that governs standby policy.
- `CameraCentral.policy` (`public let`) is never read, and goes stale the moment `setPolicy` is
  called.
- `GeotagCoordinator.heartbeatInterval` derives from `ConnectionPolicy.balanced`, not the active
  policy. The comment claims the timer and the reducer's expiry "can never disagree" — true only
  because nothing can currently change `keepAliveSeconds`; an injected policy breaks it silently.
- `SonyCBUUID.locationConfig` (DD21) is requested on every connect and then dropped by
  `default: break`.
- `UserDefaultsGeotagSettingsStore.load()` writes to `UserDefaults` (and may call `save()`) — a
  side-effecting read behind a protocol that reads as pure.

### Tooling

- **No CI.** 97 host tests that run in 17 ms, and nothing runs them automatically. A workflow
  doing `swift test` in `AlfaKit` would cover the whole pure layer.
- `Info.plist` has no `ITSAppUsesNonExemptEncryption`, so every upload prompts for export
  compliance.
- `AlfaCameraSim`: `manager.updateValue(...)`'s return value is ignored and
  `peripheralManagerIsReadyToUpdateSubscribers` is unimplemented, so a scripted FF02 notification
  can be dropped under queue pressure — surfacing as an unexplained integration-test timeout.
  `didReceiveWrite` also responds once per request; Apple's contract is one `respond(to:)` per
  callback, passing the first request.
